## 4. Deep Investigation: The Checksum & Why 512 KiB and 1 MiB Match

A critical question raised during the audit: **Why do 512 KiB ($n = 65,536$) and 1 MiB ($n = 131,072$) report the identical checksum of `44086`?**

### What the Source Checksum Actually Represents
In [`src/memory_lab.cpp`](file:///home/amans/Devfield2/experiment/memory-wall/src/memory_lab.cpp#L59-L65), `chase_kernel` is implemented as:
```cpp
static u64 chase_kernel(const std::vector<std::size_t>& next,
                        std::size_t accesses) {
    std::size_t p = 0;
    for (std::size_t i = 0; i < accesses; ++i)
        p = next[p];
    return static_cast<u64>(p);
}
```
1. **Not a Hash or Accumulator:** The return value is **not** a hash, parity check, or arithmetic sum of visited node values. It is purely the index $p$ of the single node where the traversal halts after exactly $2,000,000$ pointer dereferences starting from index 0:
   $$p_{\text{final}} = \text{permutation}^{2000000}(0)$$
2. **Repetition Invariance:** Because $p$ is reset to $0$ at the start of each repetition and the permutation array `next` is immutable, every repetition for a given size halts at the identical node.

### Why 512 KiB and 1 MiB Both Yield 44,086
Our investigation using a dedicated inspection tool ([`scratch/investigate_checksum.cpp`](file:///home/amans/.gemini/antigravity-cli/brain/3f416b99-6c20-4512-a3e3-0c313ef57a40/scratch/investigate_checksum.cpp)) uncovered two intersecting mechanisms:

#### Mechanism 1: Exact Modulo Cycle Step Alignment
The single random cycle is constructed such that node traversal visits all $n$ nodes before repeating.
When stepping $W = 2,000,000$ times through a cycle of length $n$, the final node offset from the starting position $\text{pos}_0$ is given by $W \pmod n$:
- For $n = 65,536$ (512 KiB):
  $$2,000,000 = 30 \times 65,536 + 33,920 \implies 2,000,000 \pmod{65,536} = 33,920$$
- For $n = 131,072$ (1 MiB):
  $$2,000,000 = 15 \times 131,072 + 33,920 \implies 2,000,000 \pmod{131,072} = 33,920$$
Because the quotient $30$ is an even integer ($30 = 2 \times 15$), the cycle offset remainder is **identically 33,920** for both sizes.

#### Mechanism 2: PRNG Prefix & Forward Shuffle Implementation
In GCC libstdc++ ([`bits/stl_algo.h`](file:///usr/include/c++/13/bits/stl_algo.h)), `std::shuffle` implements a forward Fisher-Yates variant:
It loops forward from index $i = 1$ to $n - 1$, generating random swap targets $j \in [0, i]$ using `std::mt19937_64(12345ULL)`.
- For $n = 65,536$, the shuffle processes elements $1 \dots 65,535$.
- For $n = 131,072$, the shuffle processes elements $1 \dots 65,535$ using the **exact same initial PRNG sequence**. At step $65,535$, the lower half of the 1 MiB array is bit-for-bit identical to the entire 512 KiB array.
- In the 1 MiB array, subsequent swaps for $i = 65,536 \dots 131,071$ select swap indices $j \in [0, i]$. Roughly half of these swaps target the upper half $[65536, 131071]$, leaving approximately half ($32,748$ out of $65,536$) of the lower-half indices untouched.
- By deterministic PRNG draw under GCC 13.3.0:
  - $\text{pos}_0 = 12,864$ (the location of node 0) was **not** swapped during steps $65,536 \dots 131,071$.
  - $\text{target\_idx} = (12,864 + 33,920) = 46,784$ was **also not** swapped during steps $65,536 \dots 131,071$.
  - In both arrays, `order[46784] == 44086`.

#### Empirical Verification & Traversal Path Divergence
A dedicated standalone verification utility ([`scripts/verify_cycle_checksum.cpp`](file:///home/amans/Devfield2/experiment/memory-wall/scripts/verify_cycle_checksum.cpp)) was compiled and executed to verify the actual generated cycle structures without running benchmarks:
1. **Single Cycle Integrity:** Both arrays form a single closed Hamiltonian cycle visiting all elements ($65,536$ for 512 KiB, $131,072$ for 1 MiB) before returning to node 0.
2. **Immediate Path Divergence:** Although both walks start at node 0, they diverge on the very first jump:
   - At step 0: $\text{curr}_1 = 0$, $\text{curr}_2 = 0$.
   - At step 1: $\text{curr}_1 = \text{next}_1[0] = 45,150$, whereas $\text{curr}_2 = \text{next}_2[0] = 79,530$. Node 0 in the 1 MiB array points into the upper half ($> 65,536$).
3. **Shared Edges:** Only $16,252$ out of $65,536$ directed edges ($24.80\%$) are shared between the two permutation graphs.
4. **Coincident Steps:** Across the 2,000,000 steps, $\text{curr}_1 == \text{curr}_2$ on only $508,111$ steps ($25.41\%$).
5. **Convergence on Terminal Node:** At step $2,000,000$, both walks terminate on node index **`44086`**, purely because $p_{\text{final}} = \text{order}[(\text{pos}_0 + (W \pmod n)) \pmod n]$ evaluates to $\text{order}[46,784] = 44,086$ in both permutations.

#### Separation: Verified Facts vs. Implementation-Dependent Mechanics
To preserve scientific rigor, we distinguish what is physically and mathematically verified from what is compiler-specific:
- **Verified Facts:**
  - The source code return value is the terminal node index $p_{\text{final}}$, not an accumulator or hash.
  - $2,000,000 \pmod{65,536} \equiv 2,000,000 \pmod{131,072} \equiv 33,920$ is an exact arithmetic identity.
  - The two walks diverge immediately at step 1 and follow vastly different paths through memory before landing on node 44,086.
- **Implementation-Dependent Mechanics:**
  - The C++ standard does not specify the iteration order or random number consumption pattern of `std::shuffle`.
  - The retention of indices 12,864 and 46,784 is an artifact of GCC 13.3.0 libstdc++'s forward shuffle and the chosen seed `12345ULL`.
  - Compiling with Clang/libc++ or MSVC STL will generate a different permutation and different terminal node indices.

#### Scientific Conclusion
> [!CAUTION]
> **Checksum Equality Does NOT Prove Traversal Equivalence:**
> The identical checksum of `44086` between 512 KiB and 1 MiB is an algebraic consequence of the even quotient ($30 = 2 \times 15$) and the deterministic PRNG draw.
> - The two working sets have completely different memory footprints (524,288 bytes vs. 1,048,576 bytes).
> - The 1 MiB cycle touches 131,072 distinct virtual addresses, while the 512 KiB cycle touches only 65,536 distinct virtual addresses.
> - Checksum equality must never be conflated with execution equivalence or benchmark correctness.

## 7. Evidence Separation: Scientific Guardrails

In adherence to strict experimental guidelines:

### Observed
- Elapsed wall-clock time per 2,000,000 operations across 13 working-set sizes and 2 verification re-tests.
- Deterministic checksums identical across all 5 repetitions for each configuration.
- Checksums identical between 512 KiB and 1 MiB (`44086`).
- Pre- and post-run binary SHA-256 (`9c71a0984e4001bac4a60b6bfcfbcce9e0cd1e760e9024dafc9a042c8cb390a0`).

### Calculated
- Derived per-step latency: $t_{\text{step}} = (\text{seconds} \times 10^9) / 2,000,000$.
- Type 7 linear interpolation quartiles (Median, Min, Q1, Q3, Max, Range, IQR).
- Latency scaling ratio: $\frac{100.3209\text{ ns/op}}{1.2392\text{ ns/op}} = 80.96\times$.
- Verification replicability: 1 MiB drift of $0.0412$ ns/op (0.89%); 16 KiB drift of $0.1947$ ns/op (13.22%).
- Cycle traversal step offset remainder: $2,000,000 \pmod{65,536} = 33,920$ and $2,000,000 \pmod{131,072} = 33,920$.

### Plausible Architectural Interpretations
- The initial flat region $\le 32$ KiB is consistent with L1d cache residency (~5–8 CPU clock cycles).
- The intermediate step changes align closely with nominal cache capacities reported by `lscpu` (48 KiB L1d and 2 MiB L2).
- The steep latency ascent beyond 8 MiB towards 64 MiB is consistent with the compound latency of LLC misses, DRAM access latency, and multi-level page table walks / TLB misses across 16,384 virtual 4 KiB pages.

### Unknowns & Guardrails
- **No PMU / Hardware Counter Data:** We do not claim measured L1/L2/L3 miss rates, bus transactions, or physical memory bandwidth. WSL2 guest kernel does not expose PMU counters (`perf` unavailable).
- **TLB vs. DRAM Confounding:** The relative latency contribution of translation lookaside buffer misses versus DRAM column access strobe (CAS) latency cannot be decoupled from wall-clock timing alone.
- **Core Heterogeneity & Affinity:** Whether guest threads executed on physical Performance-cores (Golden Cove) or Efficient-cores (Gracemont) is unverified from within the WSL2 guest.
